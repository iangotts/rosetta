Comparative Analysis

Graphify vs Rosetta

Two knowledge graphs, two philosophies. One is an open-source tool that auto-extracts structure from a codebase at build time. The other is a governed, curated knowledge layer that serves Salesforce methodology to agents at runtime. This is where they meet, where they diverge, and what each can do for the other.

Executive Summary

They are not competitors. They are different categories that happen to share a noun.

Both are described as "knowledge graphs that give AI the right context." That surface similarity hides a fundamental split. Graphify is a developer comprehension tool — point it at a folder, it parses code locally and emits a queryable graph so an AI coding assistant stops grepping blind. Rosetta is a governed operational knowledge layer — a curated Neo4j canonical inventory of Salesforce methodology that acts as a runtime "co-driver," surfacing trusted guidance at the moment of need.

The honest verdict: complementary, not competitive. Where they overlap — graph-as-context-for-AI — they embody opposite design philosophies: emergent auto-extraction versus governed curation. Graphify is a candidate tool inside the Rosetta programme, not a threat to it.

What Each One Is

A tool and a layer

Graphify

Open-source · Build-time · Code-centric
  • An AI-coding-assistant skill (Claude Code, Codex, Cursor, etc.) that turns a folder of code, docs, papers and images into a queryable graph.
  • Construction: Tree-sitter AST locally (code never leaves the machine) + LLM semantic extraction for prose and images.
  • Clustering: NetworkX + Leiden community detection on topology alone — no embeddings, no vector store.
  • Output: three committed files — graph.html, graph.json, GRAPH_REPORT.md — plus optional Neo4j/Cypher export, MCP server, watch mode.
  • Trust model: every edge tagged EXTRACTED / INFERRED / AMBIGUOUS — honest about found vs guessed.
  • Maturity: ~58K GitHub stars, ~1.2M PyPI downloads, YC-backed, single primary maintainer (Safi Shamsi).

Rosetta

Governed · Run-time · Methodology-centric
  • A governed knowledge layer (KeenanVision / Ian Gotts) unifying fragmented Salesforce documentation, product naming and methodology into one source of truth.
  • Construction: a Cypher-first content pipeline over a governed semantic model on Neo4j — a formal entity-and-relationship canonical inventory.
  • Ontology: a deliberate Phase → Stage → Task hierarchy with RASCI, versioning and harmonisation rules under a design authority.
  • Delivery: serves context to agents at runtime via RAG middleware, MCP and SKILL.md inside Slack and Cowork — "no new interface, no ramp time."
  • Trust model: curated gold-standard content; the canonical inventory doubles as compounding eval ground truth.
  • Positioning: the "co-driver" that amplifies the architect's judgement — proof of value in 5 days, activation in 24 hours.

Positioning

The 2×2: extraction vs governance, code vs business knowledge

The two axes that actually separate them are how the graph is created (emergent auto-extraction at the bottom, governed curation at the top) and what it is a graph of (code & repository structure on the left, business knowledge & methodology on the right). They land in opposite quadrants. ZenAlpha is plotted as ecosystem context — a process-knowledge pipeline that sits between the two.

Markers are qualitative positions, not measured scores.

Where They Touch

The narrow overlap — and the deep philosophical contrast

Both produce a graph, both can speak MCP, and both ultimately exist to put better context in front of an AI. Graphify can even export Cypher and push to Neo4j — the same database Rosetta is built on. So at the plumbing layer they can literally meet.

But the philosophies are opposites. Graphify trusts the corpus and surfaces what is there — emergent communities, "god nodes," surprising cross-file links, all regenerated each run and explicitly flagged when guessed. Rosetta distrusts raw corpora and imposes an authored truth — harmonised, governed, RASCI-owned, versioned so every improvement compounds. Graphify answers "what does this codebase actually look like?" Rosetta answers "what is the correct, sanctioned way to do this?"

Put simply: Graphify is descriptive; Rosetta is prescriptive. A descriptive graph is a perfect input to — and audit lens on — a prescriptive one. It is a poor replacement for it.
Opportunity

What Graphify could do for the Rosetta programme

Bootstrap & audit the canonical inventory

Run Graphify over the raw Salesforce docs, methodology files and transcripts to auto-draft a first-pass entity graph. Use it as a candidate set the design authority then harmonises — faster than a blank page, with confidence tags showing what needs human judgement.

QA lens on the governed graph

Graphify's god-node and "surprising connection" analysis is a cheap structural sanity check. Run it against the curated content to find orphaned nodes, over-connected hubs, or links the harmonisation step missed.

Understand the Rosetta codebase itself

The middleware, MCP server, SKILL.md and Cowork config are real code. Graphify maps that repo so contributors trace how a query flows from Cowork → middleware → Neo4j without reading every file.

Borrow the discipline, not just the tool

Two ideas are worth importing regardless: topology-only clustering (no embedding bill) as a structural view of the inventory, and explicit found-vs-guessed tagging — a natural fit for Rosetta's ground-truth and eval ambitions.

The Moat

What Rosetta has that Graphify structurally cannot

None of the above is a threat to Rosetta's reason to exist, because Graphify cannot produce the things that make Rosetta valuable:

Governance & authority

  • Sanctioned correctness. An auto-extracted graph reflects whatever the docs say, contradictions and all. Rosetta encodes the approved answer, owned via RASCI.
  • Compounding ground truth. The versioned inventory survives model, retrieval and rubric changes — every preference pair is a permanent data point. A per-build graph has no such memory.
  • Runtime co-driver. Rosetta serves guidance live, in the flow of work. Graphify is a build-time artefact, not a production guidance layer.
  • Domain ontology. Phase → Stage → Task is a deliberate methodology model, not an emergent cluster. It is the product.

Due diligence if adopted

  • Package name. The official PyPI package is graphifyy (double-y) with many unaffiliated look-alikes — a typosquat hazard. Pin the version; prefer uv/pipx.
  • Data residency. Code stays local, but docs and images are sent to the configured LLM. For sensitive Salesforce content, route through a controlled model deliberately.
  • Self-reported metrics. The headline 71.5× token-reduction figure is the project's own number on a mixed corpus — treat as indicative, not benchmarked.
  • Single-maintainer risk. Fast-moving OSS with one primary author; fine for internal tooling, weigh before any production dependency.
Recommendation

Verdict

Complementary · Not Competitive

Adopt Graphify as an internal tool. Do not frame it as a Rosetta alternative.

Graphify and Rosetta occupy opposite quadrants: descriptive auto-extraction of code versus prescriptive governed business knowledge. They are not substitutes. The strategic move is to use Graphify upstream and around Rosetta — to bootstrap the inventory, audit the governed graph, and map the Rosetta codebase — while Rosetta remains the curated, runtime source of truth that no auto-extraction tool can replace.

If a competitive 2×2 is needed for positioning, Rosetta sits firmly upper-right (governed × business-knowledge) on its own merits here — not by construction, but because that quadrant is genuinely where the defensible value lives.
